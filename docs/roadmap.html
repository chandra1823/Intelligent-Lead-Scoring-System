Phase 1 · Shipped

The finding that shaped the model

An earlier version reported ~92% accuracy. That number came from training on columns a sales rep fills in after contacting the lead — Tags = "Closed by Horizzon" converts at 99.4%, Lead Quality = "Worst" at 2.0%. The model was reading its own answer key. Excluding them dropped accuracy to 83.3% and made it real. Phase 2 turns this one-off discovery into an automated check that runs against every customer's data.

Shipped in Phase 1

  • Leakage-free feature set — post-contact sales columns excluded, enforced by a test.
  • Calibrated hybrid ensemble — RandomForest + XGBoost + LightGBM, isotonic calibration, weighted by AUC lift so a coin-flip model earns zero weight.
  • Self-contained pipelines — each artifact preprocesses raw records itself, so training and serving cannot drift apart.
  • Ablation explanations — every field's contribution measured by re-scoring the lead with that field reset to baseline.
  • Graceful degradation — partial ensemble, then heuristic fallback; the demo never dies.
  • 24 tests covering leakage, preprocessing, weighting, ranking, API contracts, and fallback.

Honest limits

  • One dataset, one schema. The model only understands X Education's exact columns.
  • One user, no memory. No accounts, no database — scores vanish when the request ends.
  • Manual entry only. A human types one lead at a time into a form.
  • No feedback loop. Nothing records whether the prediction was right.
  • Local only. No container, no deployment path, no rate limiting.
The gap

What "clone it and connect your CRM" actually demands

The goal sounds like one feature. It is really six problems, and the hardest one is not the MCP server — it is that every customer's data looks different from every other customer's.

Their columns aren't your columns

HubSpot calls it hs_analytics_num_page_views. Salesforce calls it something else. A model trained on Page Views Per Visit cannot read either. You need a canonical schema and a mapper that gets from their fields to it.

Their answer key isn't yours

A model trained on ed-tech leads will misprice a B2B SaaS pipeline. Each customer eventually needs a model trained on their own history — but on day one they have no labelled history at all.

Scores must go somewhere

A score in a browser tab changes nothing. It has to land back in the CRM as a field a rep sees, or in a queue their morning starts with.

Real data is sensitive

Names, emails, phone numbers, employers. That brings retention rules, encryption, audit trails, and a very good reason to make self-hosting the default.

Models rot

Campaigns change, seasons change, the mix of traffic changes. Without drift and calibration monitoring, quality decays silently and nobody notices for months.

Leakage will recur

Every CRM has its own Tags column — a status field written after the outcome. Customers will train on it and get a beautiful, worthless model unless the platform catches it for them.

Phase 2 · Six tracks, all built

What to build

These are workstreams, not steps — lettered rather than numbered because there was no single required order. All six are now implemented; each card lists what was built and the module it lives in.

TRACK A

MCP server — make it agent-native

The headline feature. Someone adds your server to Claude Desktop or Cursor and asks "which leads should I call today?" — in plain language, against their real pipeline.

  • Tools — score_lead, score_batch, explain_lead, list_priority_leads, connect_source, sync_source, map_schema, push_scores, train_tenant_model, model_metrics, simulate_lead, record_outcome.
  • Resources — leads://priority, model://metrics, schema://canonical, source://{id}/mapping.
  • Prompts — packaged workflows: triage today's pipeline, explain a lead to a rep, run a weekly pipeline review.
  • Transports — stdio for local desktop use, streamable HTTP for a hosted deployment.
  • Safety — write actions (push_scores, sync_source) declared as non-readonly so clients prompt before firing.
Built  mcp_server/server.py — 17 tools, 3 resources, 3 prompts, stdio + streamable HTTP, write tools annotated so clients confirm first.
TRACK B

Universal lead connectors

One small protocol, many adapters. Adding a new CRM should be a single file, not a refactor.

  • Protocol — fetch(since), push_score(id, score), schema(), test_connection().
  • Adapters — HubSpot, Salesforce, Zoho, Pipedrive, Google Sheets, CSV upload, generic webhook. Ship two, document the interface, let contributors add the rest.
  • Sync engine — cursor-based incremental pulls, exponential backoff, partial-failure recovery, per-source sync log.
  • Credentials — OAuth where supported, encrypted at rest, never in the repo or in logs.
  • Writeback — push the score and band into a custom CRM field so reps see it where they already work.
Built  connectors/ — protocol plus CSV, Google Sheets, inline/webhook and HubSpot (with writeback, paging, and 429 backoff). A new adapter is one file.
TRACK C

Bring-your-own-data machine learning

The hardest track, and the one that decides whether this is a real product or a demo with connectors bolted on.

  • Canonical schema — a CRM-agnostic lead: engagement, provenance, profile, intent, outcome. Every adapter maps into it.
  • Schema mapper — fuzzy name matching plus type and cardinality heuristics, with an LLM assist for the leftovers, then a human confirmation screen. Never silently guesses.
  • Automated leakage detector — flags any single feature that predicts the outcome almost perfectly, or any category whose conversion rate is above 95% or below 5%. This is Phase 1's discovery turned into a guardrail every customer gets.
  • Cold-start tiers — see the table below. A customer with no labelled data still gets something useful on day one.
  • Per-tenant training — scheduled retrains, champion/challenger comparison, automatic rollback when the challenger underperforms.
Built  ml/canonical.py, ml/mapping.py, ml/leakage.py, ml/training.py. The detector independently rediscovers the Tags leak; the mapper resolves renamed CRM columns and flags the rest.
TRACK D

Production platform

The unglamorous half. Nothing here is novel; all of it is required.

  • Persistence — Postgres with Alembic migrations: tenants, sources, leads, scores, outcomes, models, audit log.
  • Background jobs — Redis + RQ for sync, batch scoring, and training. Long work must not block a request.
  • Multi-tenancy — scoped API keys, row-level isolation, per-tenant model registry.
  • Deployment — Dockerfile, docker-compose for the full stack, GitHub Actions for tests and image builds, health and readiness probes.
  • Hardening — rate limiting, structured logging with request IDs, error tracking, graceful shutdown.
Built  SQLAlchemy models, API keys, encrypted credentials, rate limiting, request IDs, probes, Dockerfile, docker-compose with Postgres, GitHub Actions.
TRACK E

Decision intelligence — beyond a number

A probability is not a decision. This track is where the product stops describing leads and starts directing effort — and it's the strongest differentiator against the scoring feature every CRM already ships.

  • Capacity-aware ranking — a team that can make 50 calls a day wants the top 50 leads, not everything above 0.5. The fixed threshold is an arbitrary default worth removing.
  • Expected-value scoring — rank by probability × deal value, so a 40% shot at a large account outranks an 80% shot at a small one.
  • Time-to-conversion — survival modelling to answer "who is going cold?", not just "who is good?".
  • Next best action — uplift modelling on historical touches: which leads actually respond to a call versus an email, rather than who converts anyway.
  • Score decay — a lead scored on stale engagement should visibly lose confidence over time.
  • Segment thresholds — different cut-offs per channel or region, tuned to each segment's base rate.
Built  ml/decisions.py — capacity ranking, expected value, score decay, segment thresholds, decile lift. Next-best-action ships rule-based and says so; uplift needs treatment data.
TRACK F

Trust, monitoring, and privacy

Anything scoring real people needs to be auditable, and anything holding real contact data needs to be defensible.

  • Drift monitoring — population stability index per feature, alerting when input distributions move.
  • Calibration monitoring — rolling Brier score and reliability curves against actual outcomes, so silent decay becomes visible.
  • Prediction log — every score stored with its inputs, model version, and explanation. Required for "why was this lead deprioritised?".
  • Fairness review — scores checked for disparity across country and city; documented, since the dataset carries geography.
  • Privacy — PII encrypted at rest, excluded from logs, configurable retention and deletion, self-hosting as the default posture.
  • Model cards — auto-generated per tenant model: training window, features, metrics, known limits.
Built  ml/monitoring.py — PSI drift, calibration/ECE, prediction log, audit trail, PII stripping. Fairness review and model cards are not built yet.
Track C detail

Cold start: useful on day one, better by month three

A new customer has zero labelled outcomes. Refusing to score until they accumulate thousands is how a product dies during the trial. The tiers degrade honestly instead, and the interface always says which tier is active.

TierLabelled leadsWhat runsWhat the user is told
0 · Generic 0 Phase 1 base model over mapped fields, plus engagement heuristic "Generic scoring — not yet trained on your data"
1 · Recalibrated 1 – 500 Base model, isotonic recalibration on their outcomes "Tuned to your conversion rate"

Why MCP is the right bet here

Lead triage is a conversation, not a dashboard. A rep's real question is "who do I call and what do I say" — which needs ranking, explanation, and context stitched together on the fly. Exposing the engine as tools lets the assistant compose those steps, instead of you predicting every screen a user might want.

Risks

What could go wrong, and the plan for it

RiskMitigation
Customers train on leaky columns
Every CRM has a post-outcome status field		 Automated leakage detector gates every training run; suspicious features are quarantined and surfaced for confirmation, never used silently.
Too little data to train Cold-start tiers with a hard minimum before a tenant model is promoted; the base model keeps serving until then, clearly labelled.
Schema mapping guesses wrong Mapper proposes with confidence scores; a human confirms before first training. Mappings are versioned and reversible.
CRM rate limits and API drift Cursor-based incremental sync, exponential backoff, per-adapter conformance tests pinned to API versions.
PII handling Self-hosted by default, encryption at rest, PII excluded from logs and from features, configurable retention and hard delete.
Silent model decay Drift and calibration monitors with alerting; scheduled retrains; automatic rollback when a challenger underperforms.
Scope outruns one developer Milestone gates — each one ships something usable. Two adapters, not seven; document the interface and let contributors extend it.
Definition of done

How to know Phase 2 worked

Adoption

Under 15 minutes from git clone to a first score against the user's own CRM, without reading source code.

Model quality

Tenant models beat the base model on their own holdout for most customers with Tier 2 data or better.

Business lift

Top-decile conversion at least 3× the base rate — the number that justifies changing how a sales team works.

Calibration

Brier below 0.15 and expected calibration error below 0.05, so a 70% score means roughly 70%.

Performance

p95 under 200 ms for a single score; 10,000 leads scored in under 30 seconds.

Reliability

A failing CRM sync never takes scoring down; degraded modes are visible in /health, never silent.

Deliberately out of scope

Phase 3 horizon

Worth naming so they don't creep into Phase 2 and stall it. Each assumes Phase 2 is already running against real pipelines.

  • Hosted multi-tenant SaaS — billing, org management, SOC 2 posture.
  • Conversation intelligence — score from call transcripts and email threads, not just form and clickstream data.
  • Marketplace adapters — community-contributed connectors with a certification process.
  • Automated outreach — draft the first-touch message, with a human approving every send.
  • Account-based scoring — roll lead scores up to company level for B2B pipelines.
  • Causal experimentation — built-in holdout groups to measure whether the scoring changed revenue, not just ranking.
